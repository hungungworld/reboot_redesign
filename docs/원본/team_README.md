# 📊 REBOOT US 마케팅 대시보드

> 무역 AX2기 2차 미니프로젝트 3조 · 알디콤을 모티브로 한 신규 숙취해소 젤리 스틱 **REBOOT**의 미국 마케팅 업무를 한곳에서 확인하고 관리하는 **HTML 대시보드**

광고 문구 점검, 콘텐츠 제작, 고객 응대, 시장 분석, 성과 분석 등 마케터의 주요 업무를 한 화면에서 처리하고, 반복 업무 시간을 줄이는 것이 목표입니다.

> ⚠️ 현재 버전은 샘플 데이터와 규칙·템플릿 기반 **시연본**입니다. 외부 API와 AI 모델은 대부분 연결되지 않았으며, 실제 광고 심의나 규제 적합성을 판정하지 않습니다. **판정 결과 PASS(규칙 미탐지)는 법적 승인이 아닙니다.**

## 1. 실행 방법

### 기본 (설치 없음)
1. 저장소를 내려받거나 `git pull`
2. `index.html`을 **더블클릭** → Chrome 또는 Edge로 열림
3. 로그인 후 왼쪽 메뉴에서 기능 선택

인터넷이 없으면 웹폰트 대신 기본 글꼴로 보입니다.

### Google 로그인이 필요한 기능 (Gmail 등)
더블클릭(`file://`)으로 연 화면에서는 Google 로그인이 동작하지 않습니다. VS Code 확장 **Live Server** 등으로 `http://localhost`에서 열어야 합니다.

### 서버 기능 (선택 · 경고장 크롤링, Gmail, 키가 필요한 API)
브라우저 보안 규칙 때문에 fda.gov 크롤링, 키가 필요한 API는 HTML만으로는 동작하지 않습니다. 필요할 때만 서버를 켭니다.

```bash
cd server
pip install -r requirements.txt
python app.py              # 실행 주소는 터미널에 표시됨
```

`server/.env`는 `server/.env.example`을 복사해서 만들고, 키 값은 각자 넣습니다. `.env`는 깃에 올리지 않습니다.

## 2. 메뉴 구조와 담당

자료 방식: **API** 외부 서비스에서 자동으로 받기 · **크롤링** 웹페이지에서 수집 · **AI** AI가 생성·판정 · **수동** 사람이 직접 정리 · **더미** 시연용 가짜 데이터 · **입력** 화면에서 사용자가 입력 · **자동** 앱이 알아서 저장·처리

```text
    ├─ core-stub.js           #   공통 core/ 대역 (register·expose·use·store)
    ├─ settings-stub.js       #   설정 파트 대역 (facts)
    └─ test_parts.js          #   node dev/test_parts.js — 엔진·분류·템플릿 점검
```

**왜 이렇게 나누나요?** 지금 시연본은 파일 하나에 모든 메뉴가 들어 있어서, 두 사람이 동시에 고치면 같은 파일에서 충돌이 납니다. 파트마다 자기 폴더만 고치면 Git이 자동으로 합쳐 줍니다.

**더블클릭 실행을 지키기 위한 약속**
- `<script type="module">`과 `import`는 쓰지 않습니다 (더블클릭으로 열면 동작하지 않음)
- 데이터는 `.json` 대신 `data.js`에 담습니다 (로컬 JSON을 `fetch`로 읽으면 막힘). 원본 CSV는 `docs/<파트ID>/`에 보관
- npm, React, 빌드 도구는 쓰지 않습니다
- 저장소에 올리는 것은 `index.html`·`core/`·`parts/`·`server/`(키 제외)·`docs/`·`tools/`입니다. `dev/`, `_incoming/`, `.env`, 키가 들어간 HTML은 올리지 않습니다

## 5. 파트끼리 겹치는 데이터

같은 데이터를 두 파트가 각자 만들면 코드도 겹치고, API 호출 한도(예: SerpApi 월 250회)도 두 배로 씁니다. **데이터는 한 파트만 만들고, 다른 파트는 불러 쓰기만** 합니다.

| 데이터 | 만드는 파트 (원본) | 불러 쓰는 파트 | 불러 쓰는 방법 |
|---|---|---|---|
| 검색 트렌드 · 이번 주 검색량 (SerpApi) | **인사이트 (이현경)** ※ 확정 필요 | 홈 (이현경) | `REBOOT.use('insights').searchTrend()` |
| 고객 페르소나 | 인사이트 (이현경) | 콘텐츠 (나원) | `REBOOT.use('insights').personas()` |
| 시즌 캘린더 | 홈 (이현경) | 콘텐츠 (나원) | `REBOOT.use('home').seasons()` |
| 제품 팩트시트 | 설정 (이현경) | 콘텐츠 · CS · 컴플라이언스 | `REBOOT.use('settings').facts()` |
| 광고 문구 판정 · 금지 표현 목록 | 컴플라이언스 (소준희) | CS 답변 재검사 · 파트너 가이드 · 콘텐츠 카피 | `REBOOT.use('compliance').review(text)` · `.bannedTerms()` |
| CS 문의 현황 | CS (소준희) | 홈 To-Do | `REBOOT.use('cs').stats()` |
| 크리에이터별 판매 실적 | 파트너 (records.js 담당) | 성과분석 (혁주) | `REBOOT.use('partners').creatorSales()` |
| 주문·재구매 샘플 | 인사이트 (이현경) | 성과분석 (혁주) | `REBOOT.use('insights').orders()` |
| 로그인한 사용자 | 로그인 (이현경) | 전체 (작업 로그 작성자 표시) | `REBOOT.user()` (공통 기능으로 제공) |
| 작업 로그 | 공통 (`core/`) | 설정 (이현경)이 화면에 표시 | `REBOOT.log('내용')` |
| 이번 주 To-Do | 홈 (이현경) | — | 각 파트의 `summary()`를 모아서 생성 |

> 불러 쓰는 함수 이름은 만드는 파트 담당이 정하고, 이 표에 적어서 PR로 올립니다. 이름을 바꿀 때는 쓰는 파트 담당에게 먼저 알립니다.

## 6. 코드가 겹치지 않게 하는 규칙

### 6-1. 파트 파일의 기본 모양 (모든 파트 공통)

각 파트는 자기 코드를 `(function(){ ... })();`로 감싸서 **밖으로 이름이 새지 않게** 하고, `REBOOT.register()`로 메뉴에 등록만 합니다.

```js
// tabs/compliance/static/compliance.js
(function () {
  const store = REBOOT.store('compliance');        // 저장 키가 자동으로 reboot:compliance:* 가 됨
  const { card, esc, toast } = REBOOT.ui;

  function render(el) {                            // el = 이 파트 전용 화면 영역
    el.innerHTML = card('광고 문구 사전 점검', `
      <textarea class="cmp-input" data-ref="copy"></textarea>
      <button class="btn primary" data-act="run">문구 점검하기</button>
      <div data-ref="result"></div>`);
    el.querySelector('[data-act="run"]').addEventListener('click', () => { /* ... */ });
  }

  function review(text) { /* 판정 로직 */ }
  function bannedTerms() { /* 금지 표현 목록 */ }

  REBOOT.register({
    id: 'compliance', icon: '🛡️', label: '컴플라이언스', priority: 'P0', order: 30,
    title: '좋은 카피의 시작, 안전한 표현.',
    subtitle: '광고 문구를 점검하고 미국 시장에 맞는 표현을 준비하세요.',
    render,                                          // 필수
    summary: () => ({ label: '검토 대기 카피', value: store.get('pending', []).length })  // 선택: 홈 To-Do에 사용
  });

  REBOOT.expose('compliance', { review, bannedTerms });  // 다른 파트가 쓸 기능만 공개
})();
```

다른 파트의 기능이 필요하면 그 파트 파일을 고치지 않고 공개된 기능만 불러 씁니다.

```js
// tabs/cs/static/cs.js 안에서 답변 초안을 컴플라이언스로 재검사
const result = REBOOT.use('compliance').review(draftText, { channel: 'cs' });
// PASS여도 사람의 최종 승인은 따로 받습니다
```

### 6-2. 이름 규칙

| 대상 | 규칙 | 예 (compliance) | 금지 |
|---|---|---|---|
| 폴더·파일 | `parts/<파트ID>/<파트ID>.js` | `tabs/compliance/static/compliance.js` | 다른 파트 폴더에 파일 추가 |
| JS 전역 이름 | **만들지 않음** (`REBOOT` 하나만 공통) | 함수는 모두 즉시실행 함수 안에 | `function review(){}`를 밖에 선언 |
| 버튼 동작 | `addEventListener` · `data-act` | `data-act="run"` | `onclick="review()"` (전역 함수 필요) |
| CSS 클래스 | 파트 접두사 + `-` | `.cmp-input`, `.cmp-badge` | `.input`, `.badge` 새로 정의 |
| CSS 범위 | 파트 영역 안으로 한정 | `.part-compliance .cmp-input {…}` | `button {…}`, `table {…}` 전체 스타일 |
| HTML id | 가능하면 `data-ref` 사용, id는 접두사 | `id="cmp-copy"` | `id="copy"`, `id="result"` |

| 다운로드 파일명 | `reboot-<파트ID>-내용.확장자` | `reboot-compliance-review.csv` | `result.csv` |
| 파트 간 연결 | `REBOOT.expose` / `REBOOT.use` | `use('compliance').review()` | 다른 파트 변수 직접 접근 |
| 키·비밀번호 | **HTML·JS에 넣지 않음** | 서버 `.env`에서만 | 코드에 키 직접 쓰기 |

| 파트 | 접두사 | 담당 | 파트 | 접두사 | 담당 |

| login | `lgn-` | 이현경 | content | `cnt-` | 나원 |

| insights | `ins-` | 이현경 | settings | `set-` | 이현경 |

### 6-3. Git 작업 순서

자세한 규칙은 저장소 맨 위 `RULE.md` §3·§4를 따릅니다.

```text
① 처음 한 번     pre_main에서 내 이니셜 브랜치 만들기 → Publish branch     예) NW, JH, HJ, HK
② 작업 시작 전   내 브랜치에서 Fetch origin → Branch › Update from pre_main
③ 작업 · 저장    자기 파트 폴더만 · python -m pytest · python -m server 로 화면 확인
④ 커밋           feat:/fix:/docs: 무엇을 했는지     예) feat: 규제 단어 57개 R1~R10 통합
⑤ 푸시 → GitHub에서 pre_main으로 Pull Request (base가 main이 아닌지 확인)
⑥ 검토           작성자가 아닌 팀원 1명 승인 + GitHub Actions 테스트 통과
⑦ 합치기(Merge)  PM이 Create a merge commit → 개인 브랜치는 지우지 않음
```

**하지 않는 것**
- `main`·`pre_main` 브랜치에 바로 push
- 다른 파트 폴더나 공통 파일 수정 (필요하면 Issue로 요청)
- 저장할 때 자동 정렬(포맷터)로 **파일 전체를** 바꾸기. 바뀐 줄이 많아져 충돌이 생김
- 큰 작업을 PR 하나에 몰아넣기. PR 하나에는 한 가지 일만 (두 파트 담당은 한 파트씩)
- 충돌이 났을 때 혼자 판단해서 남의 코드 지우기. 팀장·PM과 같이 해결

**충돌이 났을 때**: VS Code에서 충돌 파일을 열면 '현재 변경 / 들어오는 변경'이 보입니다. 내 파트 파일이면 내가 고르고, 공통 파일이면 팀장·PM에게 알립니다.

## 7. 데이터 저장과 보안

### 브라우저 저장 (localStorage)
키는 `reboot:<파트ID>:<이름>` 형식입니다. **그 브라우저에만** 남아서 팀원끼리 공유되지 않고, 브라우저 데이터를 지우면 사라질 수 있습니다.

| 저장 내용 | 파트 (담당) | 키 | 시연본의 예전 키 |
|---|---|---|---|
| 광고 문구 심의 이력 | compliance (소준희) | `reboot:compliance:history` | `aldicom-history` · `aldicom-standalone-v1` |
| 경고장 확인 결과·사례집 후보 | compliance (소준희) | `reboot:compliance:monitor` | `aldicom-standalone-v1` |
| openFDA 조회 결과 (1분 캐시) | compliance (소준희) | `reboot:compliance:openfda-cache` | `aldicom-standalone-v1` |
| 문의·분류·상태·초안·승인자·승인 일시 | cs (소준희) | `reboot:cs:inquiries` | `aldicom-standalone-v1` |

예전 키에 쌓인 기록은 각 파트 담당이 처음 실행할 때 새 키로 옮깁니다 (한 번만).

### 로그인
- HTML만으로 만든 로그인은 **화면 구분용**입니다. 코드를 열면 누구나 볼 수 있어서 실제 보안이 되지 않습니다
- 실제 비밀번호를 쓰지 말고, 시연용 계정으로만 사용합니다

### API 키 · 비밀 정보
- **HTML·JS 파일 안에 키를 넣지 않습니다.** 브라우저 '소스 보기'만 해도 보이고, main 브랜치에 커밋하면 팀 밖으로 퍼질 수 있습니다. 키가 필요한 호출은 서버를 거칩니다
- 키는 **`server/.env`에만** 둡니다. 설명은 **줄 끝이 아니라 윗줄**에 씁니다 (FDA 광고 콘솔의 `.env` 읽기 코드는 줄 끝 설명을 값으로 읽어 버림)
- 설정 → 채널·계정 연결 화면은 **연결 상태만** 보여 줍니다. 키를 화면에 입력·저장하지 않습니다
- 실제 고객 개인정보는 입력하지 않습니다. CS 테스트는 테스트 Gmail 계정 + 가짜 문의 메일로 합니다
- 키가 들어간 파일을 실수로 올렸다면 키를 바로 재발급합니다 (FDA 광고 콘솔 zip의 openFDA 키는 재발급 필요 · 17장)

## 8. 컴플라이언스

> 담당: **소준희** · P0 · 미국에 내보낼 광고 문구(아마존 상세페이지, SNS, CS 답변, 바이어 자료)가 FDA·FTC 기준에 걸리는지 1차로 점검합니다.

### 기능

| 기능 | 자료 방식 | 하는 일 | 상태 |
|---|---|---|---|
| 단건 심의 | 입력 + 규칙 (+AI 선택) | 카피 1개 → R1~R10 판정 → 걸린 표현·이유·대체 방향. AI는 FDA 사례를 예시(Few-shot)로 2차 판정 | 규칙 판정 시연본 완료 · AI는 서버 키 있을 때만 |
| 일괄 심의 | CSV 업로드 | `copy` 열 CSV → 일괄 판정 → 결과 CSV (최대 500행) | 시연본 완료 |
| 판정 근거 사례집 | 크롤링 → 데이터 | FDA 숙취 제품 경고장 7건, 원문 인용 문구, 금지 표현 JSON | 현재 53개 · 87개로 확장 예정 |
| 한국→미국 표현 매핑 | 수동 | "한국 표현 → 미국 대안", 검토자·검토일 기록 | 현재 10쌍 · 20쌍으로 확장 예정 |
| 규칙 검증 | 자동 | 경고장 문구는 모두 걸리고, 안전 문구는 모두 통과하는지 확인 | 53개 기준 시연본 완료 · 87개 확장 후 재검증 예정 |
| 심의 이력 | 자동 저장 | 검토 요청 → 승인·반려 기록. **BLOCK 판정은 승인 불가** | 시연본 완료 |
| FDA 규제 모니터링 | API + 크롤링 + 수동 | openFDA 식품 리콜 조회, FDA 경고장 새 항목 → '사례집 후보'. 출처별 HTML 가능 여부는 10장 | 리콜 조회 시연본 완료 · 경고장 수집은 서버 이관 예정 |

### 전제
- 우리 제품은 미국에서 **일반식품(Conventional Food)**. 건강기능식품 기준은 비교용 옵션
- FDA는 2020년 숙취 제품 경고장에서 숙취를 예방·치료·완화한다는 표현을 미승인 의약품 표현으로 취급함
- 일반식품도 **영양적 가치에 기반한 구조·기능 표현**은 FDA가 인정함. R8을 일괄 수정 대상으로 두는 것은 법적 금지가 아니라 **팀의 보수적 운영 기준**
- 면책 별표(*)를 붙여도 판정은 바뀌지 않음

### 규칙 R1~R10

근거 구분: ⚖️ 공식 근거(법령·FDA/FTC 문서) · 🏢 내부 정책(팀의 보수적 기준) · 🔍 문맥 검토 필요(단어만으로 판단하기 어려움)

| 코드 | 이름 | 기본 판정 | 근거 구분 | 걸리는 예 | 대신 쓸 방향 |
|---|---|---|---|---|---|
| R1 | 질병·치료 클레임 | BLOCK | ⚖️ · 🔍 | cure, prevent, relief, detox, toxins | 섭취 시점·맛·포맷 등 사실 묘사 |
| R2 | 'hangover' 직접 언급 | BLOCK | ⚖️ · 🏢 | hangover, hang-over, 숙취 | After-Party, Morning-After Ritual |
| R3 | 안전성 보장·간 보호 | BLOCK | ⚖️ · 🔍 | protect your liver, no side effects, 간 보호 | "라벨 확인 + 전문가 상담" 안내 |
| R4 | 알코올 홍조·ALDH2 | BLOCK | 🏢 | asian glow, alcohol flush, 홍조 | 판매 문구에서 제외 |
| R5 | 효과 보장·과장 | REVISE | ⚖️ · 🔍 | guaranteed, clinically proven, 100% | 용량·포장·맛 같은 검증 가능한 사실 |
| R6 | 음주 조장 | REVISE | 🏢 | drink all night, party harder | 음주량·음주 지속 언급 안 함 |
| R7 | 의약품 오인 | REVISE | 🔍 · 🏢 | hangover pills, doctor-formulated, Nature's Aspirin | jelly stick, shot 등 식품 포맷 명칭 |
| R8 | 구조·기능 클레임 | REVISE | 🏢 | supports liver health, 알코올 대사, 보충제용 면책문구 | 삭제 또는 영양 성분 사실만 (영양 근거가 있는 표현은 규제 담당 검토 후 허용 여부 결정) |
| R9 | 인체적용시험 인용 | REVISE (B2B는 REVIEW) | ⚖️ · 🏢 | clinically tested, 임상, 인체적용시험 | B2C에서는 삭제, B2B 자료에서만 |
| R10 | 후기·리뷰 | REVIEW (보상 조건이면 BLOCK) | ⚖️ | testimonials, 5-star, 후기 | 후기도 R1~R7로 심의, 대가 관계 표시 |

근거 메모 (초안 · {확인 필요: 규제 담당 확인 후 확정})
- **R1·R2**: 질병 예방·치료 주장은 의약품 표현이 됨 (2020 숙취 제품 경고장). 다만 `detox`·`relief`는 문맥에 따라 다르고, 'hangover'를 단순 언급만 해도 막는 것은 팀 기준
- **R3·R5·R9**: 효과·안전성·임상 주장은 FTC가 과학적 근거(실증)를 요구함. `100%`처럼 효과 주장이 아닌 쓰임(예: 100% juice)은 문맥 검토
- **R4·R6**: 직접 금지 조문이 아니라 브랜드·플랫폼 리스크를 줄이기 위한 팀 기준
- **R7**: 약처럼 보이는 표현은 제품의 '의도된 용도'를 판단하는 요소가 될 수 있음. 단어 하나로 확정하지 않음
- **R8**: 일반식품도 영양적 가치에 기반한 구조·기능 표현은 가능함. 팀은 근거 자료를 확보하기 전까지 보수적으로 REVISE 처리
- **R10**: FTC 추천·후기 지침과 소비자 리뷰 규칙 (대가 관계 표시, 긍정 후기를 조건으로 한 보상 금지)

> **아직 규칙에 없는 것:** 당 함량 표시(`Low sugar`·`저당` 등)는 R1~R10 어디에도 걸리지 않습니다. 미국은 "Low sugar" 표시를 허용하지 않으므로 규칙 추가 여부를 정해야 합니다 (16장 정할 것 8, 11장).

### 판정 5단계

| 판정 | 화면 표시 | 뜻 |
|---|---|---|
| BLOCK | 사용 불가 | 위법 소지가 큼 → 문장을 통째로 바꿈 |
| REVISE | 수정 필요 | 과장·음주 조장·약처럼 보임·구조기능 → 고쳐서 재점검 |
| COND | 조건부 | 건강기능식품 기준 비교용 (우리 제품엔 거의 해당 없음) |
| REVIEW | 검토 필요 | 후기·리뷰 등 사람이 판단 |
| PASS | 규칙 미탐지 | 등록된 규칙에 안 걸렸다는 뜻일 뿐 **법적 승인이 아님** → 담당자 최종 승인 필요 |

### 채널
`b2c` B2C 광고·SNS · `amazon` 아마존 상세페이지 · `cs` CS 답변 · `b2b` B2B 바이어 자료 (채널에 따라 R9 판정이 달라짐)

### 다른 파트에 공개하는 기능

| 함수 | 돌려주는 것 | 쓰는 파트 |
|---|---|---|
| `review(text, { channel, category })` | `{ verdict, findings[], codes }` · 기본 `b2c` / `FOOD` | CS · 콘텐츠 (나원) · 파트너 가이드 (혁주) |
| `bannedTerms()` | 금지 표현 `[{ term, code, verdict, ko[] }]` | 인플루언서·파트너 가이드 |
| `rules()` | R1~R10 코드·이름·판정·근거 구분·이유·대체 방향 | 화면 안내용 |
| `summary()` | 홈 카드용 한 줄 요약 | 홈 |

### 자료 출처

| 자료 | 출처 | 방식 |
|---|---|---|
| 경고장 7건 (2020-07-23 발행, 07-29 공개) | FDA 숙취 제품 경고장 (Double Wood, Ebnsol, Vita Heaven, Happy Hour Vitamins, LES Labs, Mind Body & Coal, Purple Biosciences) | 크롤링 · 원문 그대로 |

| 숙취 표현이 허용된 의약품 라벨 | openFDA `drug/label` | API |

| 구조·기능 클레임 조문 | eCFR 21 CFR 101.93 (건강기능식품 기준 · 일반식품 비교용) | API |

그 밖의 규제 출처는 10장에 있습니다. FDA 경고장 인용 문구는 **원문 그대로** 둡니다 (대괄호 `[]`, `. . .`도 원문 표기).

### 운영 원칙

## 9. 고객 응대 (CS)

> 담당: **소준희** · P1 · 고객 문의를 모아서 유형을 나누고, 답변 초안을 만들고, 컴플라이언스로 재검사한 뒤 담당자에게 넘깁니다. 답변은 자동으로 보내지 않습니다.

**컴플라이언스와의 관계:** CS 답변 초안은 발송 전에 반드시 컴플라이언스로 다시 점검합니다. 판정이 **BLOCK**이면 보낼 수 없고, PASS여도 **모든 답변은 담당자 최종 승인**을 거쳐야 Gmail 초안으로 넘어갑니다.

### 기능

| 기능 | 자료 방식 | 하는 일 | 상태 |
|---|---|---|---|
| 문의함 | Gmail API (서버) · 더미 | 문의 목록, 긴급(부작용) 우선 정렬, 응답 기한 표시 | 더미 12건 시연본 완료 · Gmail은 서버 연동 예정 |
| 문의 분류 | 규칙 (+AI 예정) | 제목·본문 키워드로 C1~C10 자동 분류, 담당자가 수정 가능 | 시연본 완료 |
| 답변 초안 | 템플릿 (+AI 예정) | 유형별 영문 템플릿에 이름·주문번호·배송 정보 채우기 | 시연본 완료 |
| 컴플라이언스 재검사 | 자동 | 초안을 `review(…, {channel:'cs'})`로 점검, BLOCK이면 발송 불가 | 시연본 완료 (내장 판정 함수) · `REBOOT.use('compliance')` 연동 예정 |
| 에스컬레이션 | 자동 | 부작용·건강·환불·불만 문의는 지정 담당 확인 체크 필수 | 시연본 완료 |
| 최종 승인 | 입력 | 모든 초안(PASS 포함) 담당자 승인 · `[확인 필요]`가 남아 있으면 승인·초안 내보내기 차단 | 예정 |
| 부작용 접수 | 입력 | 신고 양식, 빠진 항목 표시, 심각 여부 판정 | 시연본 완료 |
| 답변 템플릿 | 데이터 | 유형별 템플릿 + 각 템플릿의 컴플라이언스 결과 | 시연본 완료 |

### 문의 유형 C1~C10

| 코드 | 유형 | 처리 방식 | 담당 | 응답 기한 | 팀 태그 |
|---|---|---|---|---|---|
| C1 | 부작용 신고 | 🔴 즉시 에스컬레이션 | 품질·규제 담당 | 1시간 | 불만·건강 |
| C2 | 건강·복용·효능 | 🟠 담당자 필수 | CS 리드(건강) | 24시간 | 효과 |
| C3 | 환불·교환 | 🟠 담당자 필수 | CS 리드 | 24시간 | 환불 |
| C4 | 포장·품질 불량 | 🟠 담당자 필수 | 품질 담당 | 24시간 | 포장 |
| C5 | 배송 | 🟢 자동 초안 | CS 담당 | 24시간 | 배송 |
| C6 | 제품 정보 (맛·성분·알레르기) | 🟢 자동 초안 | CS 담당 | 24시간 | 맛 |
| C7 | 가격·프로모션 | 🟢 자동 초안 | CS 담당 | 24시간 | 가격 |
| C8 | 리뷰·평점 (불만) | 🟠 담당자 필수 | CS 리드 | 24시간 | 불만 |
| C9 | B2B·대량 구매 | 🔵 영업 전달 | 해외영업 {확인 필요} | 48시간 | — |
| C10 | 기타·협업 제안 | ⚪ 다른 파트 전달 | 인플루언서·파트너 (혁주) | 72시간 | — |

- 분류 순서: C1 → C9 → C8 → C10 → C2 → C3 → C4 → C5 → C7 → C6. 아무것도 안 걸리면 C10
- '자동 초안'은 초안을 자동으로 만든다는 뜻이며, 최종 승인은 다른 유형과 똑같이 사람이 합니다

### 처리 흐름

```text
문의 수신 (Gmail 또는 더미)
  → 자동 분류 C1~C10 (담당자 수정 가능)
  → 유형별 템플릿으로 답변 초안
  → 컴플라이언스 재검사 (channel: cs)        ─ BLOCK이면 중단
  → [확인 필요] 남았는지 확인                 ─ 남아 있으면 중단
  → [즉시 에스컬레이션·담당자 필수 유형] 지정 담당 추가 검토
  → 담당자 최종 승인 (모든 초안, PASS 포함)
  → Gmail 답장 초안 만들기 (서버) / 발송 완료 표시 (시연)
  → 종결
```

상태: `답변 대기` → `검토 중` → `승인` → `Gmail 초안 생성` / `발송 완료` → `종결`

### 발송을 막는 규칙

| # | 조건 | 적용 범위 | 상태 |
|---|---|---|---|
| 1 | 초안에 컴플라이언스 **BLOCK** 표현이 있으면 발송 불가 (어떤 표현인지 화면에 표시) | 모든 초안 | 시연본 완료 |
| 2 | 초안에 `[확인 필요]`가 남아 있으면 최종 승인·Gmail 초안 내보내기 불가 | 모든 초안 | 예정 |

### 답변 원칙
- 건강·복용 문의(C2)에는 개인 의료 조언을 하지 않고, 라벨 확인과 의사·약사 상담을 안내
- 효능을 약속하는 표현(숙취 해소, 간 보호 등)은 쓰지 않음 (재검사에서 걸림)
- 확인되지 않은 정보는 `[확인 필요]`로 남김 (예: 맛은 팩트시트 확정 전까지 `[확인 필요: 제품 팩트시트의 맛]`). 남아 있는 동안에는 위 규칙 2에 따라 승인할 수 없음

**심각 사례 처리 순서**

| 단계 | 시점 | 하는 일 | 기록 |
|---|---|---|---|
| ① 접수 | 고객 문의 수신 | 부작용 접수 양식 작성, C1 분류 | 접수 일시 |
| ② 긴급 검토 | 접수 후 1시간 내 (팀 내부 기준 · C1 응답 기한) | 품질·규제 담당에게 전달 → 같은 로트 이상 여부, 표시 안 된 알레르기 성분, 오염 확인 | 검토 시작 일시 |
| ③ 보고 대상 판단 | 검토 결과가 나온 시점 | 책임 주체가 해당 식품이 RFR 보고 대상 식품(섭취 시 심각한 건강상 악영향이나 사망을 일으킬 가능성이 상당한 식품)인지 판단 | **판단 일시**·판단자 |
| ④ RFR 보고 | ③에서 보고 대상으로 판단한 뒤 가능한 한 신속히, **늦어도 24시간 내** | FDA Reportable Food Registry 보고 | 보고 일시 |

- RFR의 24시간은 문의 접수(①)가 아니라 **보고 대상으로 판단한 시점(③)부터** 계산합니다. 그렇다고 ②·③을 미뤄도 된다는 뜻은 아니므로 각 단계의 일시를 모두 기록합니다
- 보고 책임 주체는 **식품시설 등록(FFR)을 제출한 시설의 책임자**입니다. 원인 확인에 24시간 넘게 걸릴 것 같으면 그 전에 보고하라는 것이 FDA 권고입니다
- {확인 필요: 우리 구조에서 등록 시설이 제조사(한국 공장)인지 미국 창고·수입자인지, ③의 판단 권한자는 누구인지 규제 담당과 확정}

## 10. 규제 모니터링 출처와 HTML 구현 가능성

HTML(브라우저)은 다른 사이트를 마음대로 읽을 수 없습니다. 그 사이트가 브라우저 호출을 허용(CORS)해야 하고, 키를 쓰면 HTML 안에 키가 드러납니다. 그래서 출처마다 **HTML에서 바로 / 서버 경유 / 수동**으로 나눴습니다.

| 출처 | 무엇을 보나 | 가져오는 방법 | 키 | HTML에서 | 판단 |
|---|---|---|---|---|---|
| openFDA 식품 리콜 | 리콜 동향 | API | 없어도 됨 | ✅ 바로 | 시연본에서 동작 확인 |
| Federal Register | FDA·USTR·CBP·FTC 새 공고 | API | 없음 | ✅ 바로 (예상) | FDA 광고 콘솔 독립 실행판이 브라우저에서 호출 · 첫 실행 때 확인 |

**HTML에서 서버 결과를 보여 주는 방법 (권장 구조)**
1. 서버(또는 매일 돌아가는 스크립트)가 위 출처를 확인
2. 결과를 `tabs/compliance/static/monitor-data.js`(예: `window.REBOOT_MONITOR = {...}`)로 저장
3. HTML은 `<script src="tabs/compliance/static/monitor-data.js">`로 읽기만 함 → 더블클릭 실행 유지, 키는 HTML에 없음
4. 처음 확인은 '기준 저장'만, 두 번째부터 🆕 새 항목 · 🔄 변경으로 표시 (한꺼번에 수백 건이 뜨지 않게)

키 발급·신청·수동 확인 방법은 [부록 A](#부록-a-키-발급--신청--수동-확인)에 단계별로 있습니다.

## 11. 수출 규제 조사 요약

> 2026-10-22 조사 · 참고용이며 관세사·미국 식품 규제 전문가 확인이 필요합니다. 규칙(R1~R10)과 제품 기획에 영향을 주는 내용만 적습니다.

### HS 코드와 관세
- HS 코드는 고르는 것이 아니라 **제품의 실제 형태·성분으로 정해짐**. 다른 코드로 신고하면 오분류 벌금 대상
- FDA 규제는 HS 코드로 달라지지 않음. 모든 식품 코드가 FDA 심사 대상이고, **표시·광고 내용**으로 식품인지 의약품인지 판단

| 형태 | 예상 HS 코드 (미국) | 일반 관세 → 한국산(KORUS) | 비고 |
|---|---|---|---|
| 짜 먹는 젤리 스틱·컵 젤리 | 2106.90.99 | 6.4% → 무관세 | CBP는 컵 젤리 간식을 2106.90으로 분류한 결정이 있음 |
| 구미·젤리 캔디 (소매 포장) | 1704.90.35 | 5.6% → 무관세 | 소매 포장이 아니고 당이 많으면 설탕 쿼터 구간(1704.90.58·68) 위험 |
| 무설탕 구미 (합성감미료) | 2106.90.99 (.85) | 6.4% → 무관세 | 설탕 과자(1704)가 아니게 됨 |
| 액상 음료 | 2202.99 / 2202.10 | 0.2¢/리터 → 무관세 | 관세는 가장 낮지만 운임 부담 |
| 환·정제·캡슐 | 2106.90 가능 | — | 약처럼 보여 R7·의약품 분류 위험 → 피함 |

- **현재 추가 관세:** 2026-02 미국 대법원이 상호관세를 무효로 판결 → 2026-07-24부터 한국산 전 품목에 Section 301 관세 12.5% (기존 관세와 합쳐 12.5% 상한). 그래서 위 형태들의 실제 관세 차이는 작음. KORUS 무관세와 함께 적용될 때의 계산은 관세사 확인 필요
- 최종 코드는 CBP 사전 품목분류 결정(binding ruling)으로 받아 두는 것을 권장

### 형태별 규제 비교 (젤리 · 저당 젤리 · 음료 · 저당 음료)

| 항목 | 젤리 | 저당 젤리 | 음료 | 저당 음료 |
|---|---|---|---|---|
| FDA 질식 위험 젤리 단속 (Import Alert 33-15 · 곤약뿐 아니라 카라기난·한천도 포함, 크기·식감으로 판단) | ⚠️ | ⚠️⚠️ 곤약 사용이 많음 | — | — |
| 산성화식품 공정 등록 (FCE·SID) | 상온 파우치 + 수분활성도 0.85 이상 + 산 첨가로 pH 4.6 이하면 해당 가능 | 같음 | 같음 | 같음 |
| 과즙 HACCP | 과즙(배즙 등)을 넣으면 그 과즙에 적용 · 수입자가 기록 보관 | 같음 | 같음 | 같음 |
| '저당' 표시 | — | ❌ 미국은 "Low sugar" 정의 없음 → 사용 불가 | — | ❌ 같음 |
| 감미료 의무 표시 | — | 아스파탐 경고문, 솔비톨(하루 50g 이상 섭취 가능 시) 설사 주의 문구 | — | 같음 |
| **종합 규제 부담** | 중간 | **가장 큼** | **가장 작음** | 작음~중간 |

**당 함량 표시 규칙 (21 CFR 101.60)** — 16장 정할 것 8의 근거
- `Sugar free`·`Zero sugar`: 1회 제공량당 당 0.5g 미만 + 저칼로리가 아니면 "not a low calorie food" 같은 문구 필요
- `Reduced sugar`·`Less sugar`: 비교 대상보다 25% 이상 적음 + 비교 대상과 감소 비율 표기
- `No added sugar`: 당·과즙 농축액 등을 전혀 넣지 않아야 함 (조건 까다로움)
- `Low sugar`: **정의 없음 → 사용 불가**. 한국 포장의 '저당' 문구를 그대로 번역하면 안 됨
- 알룰로스는 총당류·첨가당 계산에서 제외 가능 (FDA 허용) → 저당 제품에 유리

### 총 모양 젤리
- FDA 식품 규정상 모양 자체를 금지하는 조항은 없음
- 연방 모조 총기 표시법(15 U.S.C. §5001, 15 CFR 1150)은 장난감·모조품 대상이며 젤리 적용 여부는 명시 없음. 적용되더라도 38×70mm 이하 미니어처 예외, 밝은 색·반투명이면 표시 의무 충족
- 캘리포니아는 실제 총과 매우 비슷해 오인할 정도면 모조 총기로 봄 → 실물 같은 검정·회색 디자인은 위험
- 결론: **추천하지 않음** (음주 + 무기 연상, 아동 대상 마케팅 비판, 우리 R6 책임 음주 원칙과 충돌). 진행한다면 만화풍·밝은 색·38×70mm 이하·부드러운 식감·판매 채널 사전 확인

## 14. 권장 시연 순서

### 광고 문구 점검 (컴플라이언스)
1. **컴플라이언스 → 단건 심의**로 이동
2. `Prevents hangovers.` 같은 테스트 문구 입력
3. **문구 점검하기** 클릭 → 감지된 표현과 검토 안내 확인
4. **심의 이력**에서 기록 확인 ('사용 불가'는 승인 불가)

키워드가 발견되지 않았다고 해서 안전한 광고 문구로 승인된 것은 아닙니다.

### CSV 일괄 점검 (컴플라이언스)
첫 행에 `copy` 열이 있는 CSV 파일을 업로드합니다.

```csv
copy
Enjoy your evening.
Prevents hangovers.
```

- 파일 크기: 최대 1MB · 데이터 행: 최대 500행 · 권장 인코딩: UTF-8
- CSV 양식은 화면에서 다운로드할 수 있습니다

### CS 답변
1. **고객 응대 → 문의함**에서 부작용 문의(맨 위) 열기
2. 담당자 확인 체크 전에 발송을 누르면 막히는지 확인
3. 초안에 `cures hangovers`를 넣고 발송 → '사용 불가'로 막히는지 확인

### 콘텐츠 예시 생성 (콘텐츠 제작)
1. **콘텐츠 제작**에서 시즌·페르소나·결과물 선택
2. **콘텐츠 예시 생성** 클릭
3. 결과를 검토하고 텍스트 파일로 다운로드

현재 결과는 고정 템플릿입니다. 대괄호로 표시된 상품 정보는 검증된 실제 정보로 바꿔야 합니다.

### 마진 계산 (성과분석 · 기존 세일즈 · 운영)
판매가, 할인율, 수수료율, 원가, 운임·관세, 환율을 수정합니다.

- 할인 후 매출 = 판매가 × (1 − 할인율)
- 플랫폼 수수료 = 할인 후 매출 × 수수료율
- 예상 공헌이익 = 할인 후 매출 − 플랫폼 수수료 − 원가 ÷ 환율 − 운임·관세
- 이익률 = 예상 공헌이익 ÷ 할인 후 매출 × 100

원가는 원화, 판매가와 운임·관세는 달러 기준입니다. 기본값은 가상이며 광고비·세금·반품비는 계산에 포함되지 않습니다. 관세는 11장의 현재 추가 관세(한국산 12.5%)를 반영해야 합니다.

- 날짜와 시즌 카운트다운은 2026년 10월 22일 기준의 고정 표시입니다
- 판정과 답변 초안은 1차 참고용입니다. FDA의 공식 판단이나 법률 자문이 아니며, 최종 판단은 사람이 합니다
- PASS(규칙 미탐지)는 등록된 규칙에 안 걸렸다는 뜻일 뿐, 법적으로 문제없다는 승인이 아닙니다
- R1~R10에는 법적 기준과 팀의 보수적 운영 기준이 섞여 있습니다. 규칙별 근거 구분을 함께 확인합니다
- 사례집 문구는 2020년 경고장 기준입니다. 새 경고장은 사람이 확인한 뒤 추가합니다
- 제품 효능, 성분, 섭취 방법은 공식 자료로 확인해야 합니다. 가격·원가는 가상값입니다
- 고객 답변과 협업 제안 메일은 실제로 발송되지 않습니다. 시연에서는 '발송 완료'로 표시만 합니다
- 실제 고객 이름·주소·연락처는 입력하지 않습니다
- 경쟁사 사이트 크롤링 전에 robots.txt를 확인하고, 막혀 있으면 수동 수집으로 대체합니다
- 작업 로그는 시연용 기록이며 모든 행동을 보존하는 감사 로그가 아닙니다
- API 키, Gmail 인증 파일, `.env`, 키가 들어간 HTML은 깃에 올리지 않습니다

### A-1. Regulations.gov (규칙 제정·의견 수렴 문서) · 무료 키

3. `server/.env`에 `REGULATIONS_GOV_API_KEY=받은_키`
4. 시험용 공용 키 `DEMO_KEY`는 데모용이라 운영에는 쓰지 않음 · 설명서: https://open.gsa.gov/api/regulationsgov/

### A-2. CourtListener (미국 연방 법원 사건) · 무료 토큰
